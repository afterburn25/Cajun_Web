## Use and current authority

An owner prepares **Client website requests** in 20i settings after existing inventory, operation, client and administrator storage is ready. GET requests never create tables. Clients open **Cloud website requests** from Hosting services. An active primary client session and the exact current server assignment are required; support and contact-context sessions cannot submit decisions.

New requests now use the exact original signed assignment anchor and current client, original approving owner, provider profile, credential revision and assignment authority. The full retained history must authenticate. A healthy newer failed, unfinished, old or complete server-omitting observation does not prevent local submission; the request makes no claim of current provider availability. Owner dispatch still requires the latest complete cloud observation within 15 minutes and the current owner password. Missing or corrupt history, revoked authority or a changed assignment still refuses intake. Legacy adopted assignments need an explicit owner reapproval.

Domains are not trimmed, lowercased or truncated. The existing maximum of 20 distinct aliases applies. Intake sizes the complete future approval document against its existing 4,096-byte limit, so a valid but oversized domain list is rejected before saving an unfulfillable request. A client may make at most ten requests per 24 hours; the HTTP controller also limits repeated submissions. Overlapping pending or unresolved client requests are refused, and the existing shared operation still checks every prior cloud creation before dispatch.

## Retained history and authority

- `provider_cloud_site_request_events` stores canonical signed request, cancellation, decline and dispatch events. Its schema marker, ordinal/head pointer, exact audit witnesses and event sequence must agree. Unknown namespace additions, partial preparation, missing rows and paired row/audit loss do not become empty history.
- Client and owner events retain their account identity and authorization-version hash. Owner dispatch checks the original client's active database record; it never impersonates a client session. Account changes prevent new sends and may hide private client history. Owners may decline a still-pending request after an assignment changes.
- The client dispatch event and the existing operation grant/start audit commit in one existing staff-mutex transaction. The grant contains only fixed-size request/dispatch IDs and event HMAC fingerprints. No separate reservation or duplicated outcome table is introduced.
- Shared document/history validation resolves the signed request origin even outside the new controller. Own event validation and direct expected-grant comparison avoid recursive shared decoding. Missing origin cannot silently convert a client request into an ordinary owner grant.
- The existing gateway and durable operation ledger remain the sole source of dispatch outcomes. Exact replay reads that outcome with zero DNS or provider send, including after a newer inventory observation. Current owner/password, original-client and assignment authority are still checked. A different dispatch/grant identity cannot reopen a transitioned request.
- Before DNS, credential opening and transport authorization, the original client and current assignment are rechecked. Known pre-send refusal, accepted-pending and uncertain outcomes retain their distinct meanings. Interrupted or missing outcomes remain fenced; no fabricated completion or automatic retry is added.
- Cancellation and decline cannot alter a dispatched request. Exact cancellation/decline replays do not append events. Missing history requires recovery of the original records, not reconstruction from a new approval.
