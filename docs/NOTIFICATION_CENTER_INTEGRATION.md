# Notification center integration candidate

This is owner-authorized development work, not a deployed release. Base: `366d53b1ed6b367b32664f2b91ee073fc6813544`. Original notification stack reviewed: `04457d25a6b577edadcb993f62986fd568033d15` (PR #188 and predecessors). Original branches remain unchanged.

The center provides per-account directed notifications, read state and email-category preferences. Current resource ownership and staff permission are rechecked before showing or delivering a retained item. Client-support contexts cannot change another person's notification state. Project messages/replies, inquiries, private website delivery and legacy paid-invoice transitions emit local, idempotent event projections; tickets retain their existing independent unread/activity model. Notification failures do not roll back committed primary business events.

Email is separately owner-enabled for future eligible events. No GET/render operation sends mail. Processing a batch is an explicit authenticated, CSRF-protected owner POST with confirmation and a maximum of three due items. A database claim and audit commit before transport. An accepted transport records sent (not guaranteed inbox delivery). Known not-attempted outcomes have at most three attempts with bounded backoff; ambiguous transport exceptions remain uncertain. A crash or failed final write leaves sending/uncertain for operator/provider review, not automatic replay. Recipient permissions, resource ownership, opt-outs and email availability are rechecked at dispatch. Queue state stores integer epochs consistently with its schema. Email bodies link to the private account rather than copying private message bodies.

Setup is additive and requires a current owner session plus backup confirmation, not a redundant password. It rejects unknown nonempty data, unsupported markers, malformed existing tables and missing history after setup. Turning email off preserves the queue. Existing 1.26.1 archives, version identity and live website are unchanged.

Source receipt: `NOTIFICATION_CENTER_SOURCE.json`. The layered shipping guard preserves preceding proposal/ticket receipts instead of silently replacing their expected files. Test boundaries: pure model checks are not database acceptance; isolated SQL transport callbacks are not live SMTP; installed browser tests keep outbound email disabled. Native tests cover two independent concurrent dispatchers, committed claims, audit/final-write failures, current authority, recipient reassignment and opt-out, replay, bounded integer backoff, migration preservation, and exact retained records. Whole-site/update acceptance remains a separate gate.
