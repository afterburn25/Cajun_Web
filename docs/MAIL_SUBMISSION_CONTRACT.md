## Maintained protocol and encoding

Inspect and pin an exact maintained PHPMailer release with its original source/license and reproducible hashes before implementation. Initial official source inspected: [PHPMailer7.1.1](https://github.com/PHPMailer/PHPMailer/releases/tag/v7.1.1), commit `1bc1716a507a65e039d4ac9d9adebbbd0d346e15`. This is dependency research, not an imported or accepted runtime. Bundle the reviewed runtime through the established canonical dependency/build discipline only after isolated tests; no install-time downloads.

Use maintained MIME/header encoding and SMTP primitives. In the inspected release, the ordinary `smtpSend()` path can submit DATA for accepted recipients after another RCPT fails, then throw for the rejected recipient. Our first workflow requires all requested recipients to be accepted before DATA: use maintained low-level SMTP operations with a reviewed adapter, abort before DATA on any RCPT rejection, and do not treat a generic library exception as proof that nothing was sent. Never maintain an independent ad-hoc SMTP/MIME implementation.

MIME preparation is offline and deterministic for one immutable submission snapshot: fixed Message-ID, Date, From, recipient lists, subject and body. Reuse draft validation, require at least one actual recipient and preserve validated text. If the maintained library rejects or conflates addresses that draft syntax permits, refuse preparation explicitly without dropping recipients or exposing Bcc. Assert the generated message contains the exact intended visible recipients, excludes Bcc from headers, uses encoded UTF-8 and preserves decoded body bytes under documented newline rules. Bound encoded message size and line length before dispatch. Persist the exact prepared bytes/fingerprint; retries or history must not silently regenerate different content.

## Transport boundary

Only the selected saved account's SMTP host, port, verified encryption mode, username and private decrypted password may configure transport. Reuse the current public-address DNS policy and pin the chosen numeric address while validating TLS against the original hostname. No caller URL, proxy, custom CA, redirect, fallback plaintext, multi-host failover or implicit automatic retry. Reject unavailable required extensions and unsupported mechanisms rather than downgrading. EHLO/STARTTLS re-negotiation and authentication must follow the maintained library's supported protocol behavior with strict bounded I/O.

Set finite connect/read/write/overall deadlines and byte/line/command caps large enough for the bounded encoded message. The existing diagnostic channel's small probe limits cannot simply be assumed sufficient for DATA. Disable protocol debug output and sanitize finite error codes; server text, credentials, body and recipient addresses must not enter diagnostic/audit logs. Track transmission phase explicitly. A transport exception after possible DATA completion is unknown, never a clean failure inferred from an exception class. A valid final250 is accepted; a valid final negative reply is rejected; missing/malformed/truncated final confirmation is unknown. Closing/QUIT failure after a verified final250 does not undo acceptance. Interruption before a durable result leaves the stored dispatched intent unresolved, even if the process observed success.

## Current authorization and durable dispatch

Only a current authenticated staff author with `mail.send` and an unexpired enabled Send assignment for the exact enabled mailbox may prepare or submit their draft; owners also need that assignment. Deny support/client/anonymous sessions. Require CSRF and explicit confirmation of the selected sender, all recipients (including a clearly separate Bcc section), subject/body and exact draft/account revisions. A stale form or changed grant/profile must fail without network work. Template content is already a snapshot; no later template/client lookups during sending.

Persist a random opaque submission id, author/draft/account identity, exact revisions, prepared payload fingerprint/Message-ID and immutable content. A repeated browser submission of that same intent returns its existing state, never dispatches again. Serialize transitions using the established staff/account locking conventions and strict audit. Commit an exact intent before any credential exposure or network dispatch; an audit/storage failure prevents sending. Do not hold an InnoDB transaction over network I/O. Resolve DNS outside the staff mutex, recheck current authority after DNS and before decryption/dispatch, and preserve current permission checks when showing any result or history.

Represent prepared, dispatched, accepted, rejected and unresolved outcomes distinctly. A dispatch token binds submission, exact content/account revisions and the one attempt; ordinary results and any later reconciliation must name that token. No blank-text evidence or account-only receipt may resolve a different attempt. A successful result is immutable. Repeated terminal callbacks are exact replays only; conflicting/stale callbacks cannot rewrite history. No automatic retry of a dispatched/unresolved intent. A new deliberate send must be a new reviewed action with an explicit duplicate-delivery warning where previous delivery remains uncertain; define that separate retry/reconciliation experience before enabling it. Preparation, audit failure, disconnects and lost final writes must have distinct named acceptance cases.

Only explicit password-confirmed owner migration prepares additive submission storage on upgraded sites; fresh install creates empty storage when the feature is accepted. Preserve original mail/provider encryption keys and earlier records. Private content stays out of public responses, URLs, bells, logs and release fixtures. The author-only history must have no-store/no-referrer behavior and escaped previews. No invoice settlement, provider provisioning or transactional password-reset action follows an ordinary email.
