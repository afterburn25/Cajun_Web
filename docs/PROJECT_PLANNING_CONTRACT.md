## Pure public plan

Start outside deployment with `foundation/project-planning/ProjectPlan.php`, `ProjectPlanEvent.php`, named tests in `tests/project-planning/` and a scoped PHP8.2/8.4 default/no-ini workflow. Immutable canonical JSON bytes, private constructors and fresh decoded return values prevent caller aliases from changing accepted records. Reject duplicate/unknown JSON keys, reordered/noncanonical serialization, invalid UTF-8 and undocumented types. JSON is bounded to262,144 bytes per plan and786,432 per event. These are data rules, not current-access or database claims.

A plan has ordered fields `scope`, `assigned_contact`, `target_date`, `client_action`, `blockers`, `milestones`. Scope is exact multiline text up to10,000 bytes; client_action and blockers up to4,000 each. assigned_contact is an explicit client-visible contact label up to160 bytes, empty when unassigned; it does not grant an account permission or invent a staff identity. Text is preserved, including existing CRLF/CR/tab conventions in multiline values, and escaped by later views. Other control characters and invalid UTF-8 are refused. A nonempty contact label must contain non-whitespace text and no control bytes.

Dates are null or a valid Gregorian `YYYY-MM-DD` calendar date from0001 through9999. They are target calendar dates, not UTC instants, completion guarantees or inferred promises. A date can be overdue without the plan rewriting itself. Stored dates and milestone completion reflect explicit authorized staff input; timestamps in events are actual UTC save times.

Milestones are an ordered list of0–100 records. Each has ordered fields `id`, `title`, `details`, `state`, `owner`, `due_date`, `depends_on`. IDs are lowercase32-hex and unique within the project plan. Title is nonblank single-line text up to160 bytes; details is multiline text up to2,000 bytes. owner is `studio` or `client`, representing the party responsible, not a new login/grant. state is `planned`, `in_progress`, `awaiting_client`, `blocked`, `completed` or `cancelled`. Each dependency list contains0–8 distinct existing milestone IDs, in lexicographic order. Self-reference, missing dependencies and directed cycles are refused. A completed milestone requires every direct dependency to be completed. Removing a retained milestone in a later revision is refused; cancel it explicitly instead. Dependencies can be deliberately revised, with the actual before/after retained. Existing free-text milestones are not automatically parsed into these records.

## Dated plan events

An event has ordered fields `format`, `id`, `project_id`, `client_id`, `revision`, `kind`, `staff_id`, `occurred_at`, `before_sha256`, `before`, `after`, `changed_fields`. format is1. Event IDs are lowercase32-hex. Local IDs are positive integers up to2,147,483,647; revision is0–2,147,483,647; UTC timestamps are integers0–253,402,300,799. `plan_started` is revision0 with null before/hash and no changed fields: it records the plan first explicitly saved, without inventing earlier planning. `plan_updated` increments revision exactly once, keeps project/client identity, requires the actual earlier plan and SHA256 of its complete event, and cannot move time backward. Record the exact nonempty changed-field list in plan order. An unchanged save does not create an event. Retained milestone identities cannot disappear. Same-second saves retain revision order; a stale expected hash or duplicate event identity fails.

Parsing a single event is not proof of its position in retained history. Bounded chain validation checks1–100 events against the initial event or an explicitly supplied predecessor. A later native adapter must validate the complete retained chain and independent latest-head anchor, not infer history integrity from the latest plan alone. Public projection requires the supplied client identity to match and omits internal staff/project/client/hash metadata; native authorization must still verify current ownership and active account.
