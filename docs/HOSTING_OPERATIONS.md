# Durable hosting operation attempts

Unreleased HC-08 work on `codex/hosting-operations`, starting from storage5d9b719/PR81 (runtimef8001e9), stacked on journal80 and foundation79. These guarded internal functions do not expose a route, start a worker, decrypt credentials, contact20i or authorize real provisioning by themselves. There is no new release version. A separately verified provider adapter and operation-specific owner activation are still required.

`hosting_operations_claim()` checks the current owner/password, active selected client, current hosting revision and exact enabled provider profile revision under the shared staff mutex. The canonical lifecycle decides whether provision, suspend, resume or approved deprovision is permitted. Grace, disputes, two different cancellation/approval actors, retention confirmation and unresolved-attempt rules remain effective. The generic local-record API still cannot select these remote commands.

The new invocation atomically commits the lifecycle event, immutable dispatch fence and strict audit before returning a claim. Its binding captures account/client, original package terms, profile/revision, actor, operation, exact attempt, existing provider resource, time and before/after journal fingerprints. Only the invocation creating a new committed fence receives a claim. Exact replay returns null; changed identity reuse, stale revisions and overlapping attempts are refused. Loading a pending record, restoring files or reading an old claim is never permission to perform another network request. Fingerprints are comparison values, not signatures or provider authentication.

`hosting_operations_record()` is an internal finalizer for a future verified transport, not an HTTP callback or an operator-supplied observation form. It validates the committed binding and exact operation/account/attempt, then appends the canonical result and strict audit atomically. It must preserve observed reality if the initiating owner, client or provider is later disabled. Exact observation replay is idempotent; conflicting or late observations cannot settle another attempt. Missing confirmation remains uncertain, and applied provisioning without a provider resource stays unresolved. If final persistence or audit fails after a remote action, the earlier fence remains committed and no repeat claim is granted.

Immutable `hosting_resources` associations prevent the same provider resource from being assigned to a second account/client. Historical associations remain after deprovisioning; reassignment requires a separate verified migration. Existing-account operations stay tied to the original provider identity, although a newly reviewed current profile revision may be used. A result cannot substitute a different provider resource for a suspend/resume/delete operation.

Every operation load cross-checks the journal against dispatches, results, historical enabled credential-profile revisions and resource associations. Missing fences, mismatched event inputs/hashes, orphan outcomes and unknown retry/reconciliation formats are preserved and refused. There is no rebuild-from-pending fallback. Setup is additive, password checked and strict about schema/version/index/encoding/relationships. It refuses populated unrecognized operation tables and preexisting remote history lacking its durable fence.

Current active-client checks use a locking read inside their transaction, because legacy client administration can write outside the staff mutex. A native competing-process case checks that a revoked client is not accepted from an older transaction snapshot. Before network coordination is activated, serialize those client-administration writers with the same authorization guard; holding the staff mutex alone does not yet stop them.

The shared internal event writer now serves both local commands and exact operation results. It requires its owning transaction, compares current account/client/revision/fingerprint, and commits journal/event/audit together. The local owner API retains its closed command allowlist and current authorization checks; the native94-check record suite is rerun with this refactor.
