## Owner workflow

An owner explicitly enables change storage after registered-domain observations and provider operations are prepared. Each existing domain card contains a collapsed Change nameservers control. It shows the complete saved list and observation date beside a new-list field. The owner reviews the domain and proposed list and supplies their current password. Existing POST routing verifies CSRF; administrators, clients and support sessions cannot authorize the operation.

The supported subset replaces a complete nonempty set with another complete nonempty set that shares no names with the current set. This restriction follows the retained registrar SDK example; package-domain delta semantics are not substituted. Partial changes, overlap, empty sets and no-ops remain unsupported. No old-ns value is accepted from the browser. Hostnames are validated and canonicalized; local count/body limits are not registry allowances.

The original latest successful nameserver read must be fresh and match the current numeric domain ID, assignment, owner, provider profile, credential fingerprint and exact registrar source. The current and proposed sets, original observation, approval and actor authentication version are retained before credential access or DNS resolution. Changing a registrar source requires reviewing a new nameserver observation.

Request history is globally paginated independently of current domain assignments, so unlinking or reassigning a domain does not hide an unresolved request. A domain card also displays its own pending request even when that request is on a later global history page. Passwords are never repopulated; private binding fields and credential material are not rendered.

## Dispatch, uncertainty and follow-up

The dedicated `registrar.nameservers` operation uses `nameservers:<request_id>` in the shared operation ledger. Generic operation approval remains denied. One staff mutex spans admission, DNS, shared gateway dispatch and terminal recording; network activity occurs outside SQL transactions. Current owner, authentication version, link, client, profile, key and exact source are rechecked at credential/send boundaries. The SQL ledger's initial claimed row legitimately has a null operation; only that exact initial state is admitted during the gateway callback. Finished records require the exact registrar operation and request fingerprint.

Every POST response remains uncertain. Repeating the same approved request never repeats the provider write. An unresolved request fences its profile and numeric domain, including after credential changes, unlinking and client reassignment. Ordinary observation refreshes do not release that fence or present a current control value while a request remains unresolved.

Check current nameservers performs one separate quota-limited GET. The saved check binds that exact returned receipt, the original request/terminal proof, current context and a captured sequence floor. Only a new matching-context complete observation of the requested whole set can resolve the request. Different, unavailable or unfinished reads cannot. A matching observation proves neither causality nor DNS propagation.

Follow-up also requires an unreconciled durable original ledger completion: failed or uncertain, exactly one attempt, matching fingerprint and valid order/times. Missing or claimed ledger state remains fenced and does not expose an action known to fail. This is deliberately narrower than treating any attempted terminal as sufficient readback authority.

If a real dispatch finished but its local terminal audit rolled back, the original owner can explicitly restore only that missing local witness after reviewing the exact finished-ledger digest. Recovery never sends a provider request, never confirms remote success and still requires a later fresh readback. Deleting established terminal/history rows with retained counters/audits is corruption; it is not the interrupted-write recovery case.

## Storage and integration

Three dedicated tables, `provider_nameserver_change_requests`, `provider_nameserver_change_terminals` and `provider_nameserver_change_checks`, retain immutable authenticated documents. The separate namespace preserves the observation layer's closed `registered_nameserver_` table inventory. Independent counters, original audits, HMACs, grant correspondence, original read/source identity and ledger fingerprints validate history before it can release a resource fence.

Preparation checks the exact schema, columns, indexes, foreign keys, settings and audit namespace before DDL. Only a recognized ordered empty setup prefix can resume. Unknown storage, lost established markers or surviving grants/claims without original request history are refused. The settings cache is cleared inside the preparation mutex before current-owner authorization. No GET prepares storage; no unrelated renewal-date setup is enabled.

Root integrates the existing domain-card renderer, global history, dedicated controller/action permission and pending-observation hook. The canonical installer inventory is refreshed. VERSION remains 1.25.0 because this is an unreleased source candidate, not replacement release bytes.
