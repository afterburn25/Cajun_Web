## Implemented local contract

`StackCpHandoffContext` has its own operation and canonical detached document. It records the current-owner/client versions, separate auth credential revision/ciphertext digest, package/profile/key/link/source witnesses, membership/grant observations and a local permission witness. Every accepted context explicitly says **whole Stack user**, with `remote_scope_restricted=false`. Construction does not validate current database state, a live account, a session, or a cryptographic audit chain. The application must perform that validation before use.

As an initial defensive admission policy, the recorded grants must contain exactly the known `package:{id}` tuple and no others. This rejects unknown, server, domain, extra-client and duplicate tuples. It does not prevent remote grants changing after observation, narrow the token, or establish a one-package session. No remote grant changes are made. Existing `StackCpGrant` manage/read labels do not supply provider permission semantics.

`StackCpHandoffContract` returns non-executable descriptions of the six exact phases, their distinct credential roles and access-mutation status. It constructs no transport request, bearer URL or sender. Its future default destination allowlist is byte-exact `https://www.stackcp.com` plus `/login/sso`; custom origins, ports, user-info, encoded paths and query-bearing input are rejected.

`StackCpSensitiveResponse` accepts only a deliberately narrow subset of the SDK-used response fields:

- HTTP200, a flat JSON object of at most16,384 bytes and8 fields; duplicate decoded keys are rejected before whole-object decoding can erase them. Nested/unknown fields, null envelopes, malformed JSON and unsupported types are unavailable.
- Token fields: nonempty bounded text `access_token`, exact `token_type=bearer`, integer `expires_in` between1 and86,400, and exact `scope=interactive`. Optional `refresh_token` may be null or bounded text and is discarded. The SDK tests scope membership; this narrower parser refuses extra scopes rather than inferring their privileges.
- Session field: only nonempty bounded text `session_id`. Opaque values are at most4,096 UTF-8 bytes without ASCII control/whitespace bytes or DEL. These bounds and grammar are local validation policy, not the complete provider schema.
- All decoded keys and scalar values, including numeric expiry and discarded refresh fields, are checked against the caller-owned raw/Base64 general key and auth client key; session parsing also checks the exact access token. Credential roles are explicit. The parser cannot establish that the supplied credentials match the sealed/current database records; that is an application prerequisite.

The result label is `accepted_subset`, never successful login or authorization. The validated `expires_in` value is discarded: its units/session meaning are unverified, and projecting it could expose a newly returned numeric token or encoded refresh token through public metadata. Every unavailable reason is finite and contains no provider body/error/credential. An unavailable response does not prove the preceding request was unsent and must not authorize retries.

Opaque values are private and available only to an explicit consumer once per in-memory object. Wrong-phase consumption does not consume; callback failure still consumes. JSON, `var_dump` and `print_r` expose only safe metadata; serialization, restoration and cloning are refused. This is not durable single-send admission, a memory-zeroization guarantee or protection from trusted PHP reflection/object casting/`var_export`. The consumer is entrusted with the bearer value and must not log, serialize or persist it. A future application must use safe metadata explicitly and independently retain the durable consumed-intent witness.
