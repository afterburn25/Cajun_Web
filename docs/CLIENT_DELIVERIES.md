Payment processing still needs actual merchant acceptance; this independent portal work can progress without credentials or live operations.

Staff with client-workspace access upload an explicitly prepared ZIP, label its version/scope/source revision and supply handover notes. Upload validates bounded contents without extracting or executing code, produces an immutable manifest and checksum, and stores guarded files outside the web root. Drafts are private to authorized staff. Publication requires a fresh manifest review, current owner password and explicit content/license/client-scope confirmation. It never packages the agency installation or downloads arbitrary remote sources.

Every client list/detail/download is scoped to the current owned project and active identity. Portal-wide and project lists retain latest and earlier published versions. Download uses authenticated streaming with integrity verification, strict audit and single-byte-range resume; it never exposes a permanent public storage URL. Support must have its separate download grant, is revalidated and attributed. Publication does not require paid-in-full or silently withhold delivery.

Boundaries: up to 50 MiB compressed, 200 MiB expanded, 1000 entries and 32 MiB per file; 250 MiB per project / 1 GiB per installation. Reject path traversal, ambiguous/colliding paths, links/special files, encryption, nested archives, common secret/config/log/database paths, obvious embedded credentials and corrupted contents. Require HANDOVER.md and LICENSES.md. Checks do not prove absence of all secrets or transfer rights; explicit owner review is still necessary. Scope labels are standalone static site or files-only (database/content excluded). SQL/database exports, generated builds, dynamic restore orchestration, larger background jobs, automatic retention/deletion and notifications remain pending. No live deployment, provider call or customer email.

Additive owner setup preserves existing records/private files and refuses incompatible or unrecognized populated tables. Published bytes/metadata are immutable; prior downloads remain available while client access is authorized. Upload/publish retries, concurrent versions, audit/filesystem failure, unsafe ZIPs, client isolation, expired/revoked/support access, download hashes/ranges, mobile UI, fresh install and retained-1.8 update acceptance must pass before publishing v1.9.0. ## Setup and use

1. Back up database, website files, configuration and private storage (including payment master key). Merge UPDATE into the existing installation. Never run the fresh installer over an existing site.
2. As an owner, open Website deliveries, confirm the backup and enter your current password. Enable Client workspace/administrator accounts first if coming from an older release. Setup preserves existing records and refuses incompatible or unknown populated delivery tables. No downgrade after setup is claimed; restore consistent backups together if recovery is necessary.
3. Prepare a client-specific ZIP locally. Put useful HANDOVER.md and LICENSES.md at the archive root. Explain installation, excluded data/services, dependencies and transfer rights. Sanitize secrets, development history, configuration, logs and unrelated client/agency files. Use ASCII relative paths and standard stored/deflated ZIP entries. A static site requires root index.html and cannot contain server programs. A files-only package does not include a database or guarantee an independently working dynamic site.
4. Open the client project’s Website deliveries link, choose a version and accurate scope, add notes and optional Git hash, then upload a private draft. The host’s PHP upload/post limits may be lower than the feature maximum; the screen shows both. Upload validation does not execute or extract code.
5. An owner downloads and independently inspects the draft and manifest, checks both review confirmations, enters their current password and publishes it. Staff with client-workspace access may upload/review but cannot publish without owner authority. Clients then find Website downloads from their portal or project.
6. Clients keep the ZIP and SHA-256 checksum, read the included instructions/licenses and install in an appropriate environment. Original versions remain downloadable; a correction is a new version. Download authentication is rechecked, integrity is verified, and audit must succeed before bytes are streamed. HEAD and single byte ranges are supported; multiple ranges are rejected. Support needs its separate download grant and retains staff attribution.

Limits: 50 MiB compressed, 200 MiB expanded, 32 MiB/file, 1000 entries, and bounded compression expansion; 250 MiB/project and 1 GiB/site. Drafts count toward storage quotas. There is no supported deletion/automatic retention operation in this increment. Database failure during an uncertain file commit may leave an inaccessible orphan; preserve it for operator reconciliation instead of deleting potentially committed data. All backups must include the private deliveries directory. A missing or changed package fails closed and the client detail explains that it is unavailable.

No automatic email or admin notification is sent, no payment gate is imposed, and no public storage link is exposed. No live customer site was deployed to validate this release. Native archive/MariaDB, real HTTP/Chromium and retained-release upgrade evidence is retained in [the report](TEST_REPORT_1.9.0.md).
