# Reply and Forward in admin webmail

Status: implemented end-to-end on `devin/non20i-mail-replies`, continuing the preserved `codex/mail-replies-forwards` content/storage slice. Devin owns this non-20i increment; Codex and its agents own the complete 20i integration. Reply and Forward controls are wired from the exact message screen through protected copied drafts to explicit reviewed submission with RFC threading.

## Intended workflow

An administrator opens an exact currently authorized message and selects Reply or Forward. The server must revalidate the actor, incoming mailbox, outgoing mailbox, account revisions, INBOX UIDVALIDITY and UID before obtaining content or creating a draft. Do not trust posted original-message content or recipient headers. Preserve current CSRF/session/support restrictions, bounded reads, explicit actions and private responses.

Create an ordinary editable private draft. Reply derives recipients from parsed Reply-To, or From only when Reply-To is absent. An invalid or unsupported reply address must remain visible as unavailable; do not guess another recipient. Forward starts with no recipients. Show quoted content and any omission explicitly. Neither action may send automatically; the existing saved-draft review and explicit Send process remains required. Existing submission identity, replay prevention, unknown-outcome handling and server-acceptance-versus-delivery wording must remain intact.

Reply context must survive draft edits, exact submission snapshots and maintained MIME preparation. Preserve existing saved drafts, submission fingerprints and dispatch history when adding storage. Incoming copied content remains subject to current mailbox access. Forwarded content must not expose hidden recipients, raw message headers, attached files or another mailbox's data.

## Implemented content components

`foundation/mail-compose/MessageThread.php` represents parsed conversation identifiers without I/O, authorization, persistence or MIME generation. It is outside the deployment tree and has no application call site. `none()` supplies empty context for new messages/forwards. `reply()` carries the exact parent Message-ID into In-Reply-To, uses parent References before appending the parent ID, or falls back to a single parent In-Reply-To when References is absent. Missing identifiers stay missing. These construction rules follow [RFC 5322 section 3.6.4](https://www.rfc-editor.org/rfc/rfc5322#section-3.6.4).

The component accepts modern dot-atom identifiers and no-fold literals as parsed tokens, preserving case and exact bytes. It refuses controls, injected headers, external whitespace, obsolete quoted identifiers and malformed stored shapes. Its application bounds are 512 bytes per identifier, 32 references and 4,096 bytes for the joined References value; these are implementation limits, not RFC-wide limits. It refuses overflow instead of silently cutting history. A later receiving adapter must distinguish unavailable/unsupported context from an invented successful parse and keep the message-reading path honest.

Arrays are copied element by element so external PHP references cannot mutate accepted context. Strict saved-shape reconstruction revalidates identifiers. This establishes data validity only; the application still has to prove authority and provenance.

`ReplyMetadata.php` uses the pinned receiving envelope validation and maintained MIME parser to select a structured Reply-To list, falling back to From only when Reply-To is absent. Empty, duplicated, malformed or unsupported metadata cannot silently select another recipient. The raw syntax guard accepts modern bare addresses, display names, quoted names and bounded comments; it rejects groups and obsolete/quoted/non-ASCII local parts outside the existing Send contract. This guard is necessary because the maintained parser can join whitespace inside a malformed address and ignore trailing text without an error. It extracts only selected recipient and conversation headers; body directives, Bcc and unrelated recipients are never reply recipients. Dependency diagnostics are not exposed. Invalid reply metadata does not change the existing message-reading path.

`ReplyDraft.php` runs the existing bounded body decoder and constructs ordinary editable DraftContent. Reply retains validated conversation identifiers; Forward begins without recipients or inherited thread headers. Subjects preserve an existing appropriate prefix and explicitly report shortening. Quoted text stays valid UTF-8 within the draft byte limit, with an explicit notice when it is shortened or no supported plaintext exists. Raw headers, hidden recipients and MIME attachments are excluded. Multiple inline bodies are not silently concatenated; their omission is disclosed. These classes remain outside deployment and perform no account authorization, storage, network or sending.

## Application integration contract

The next layer must record an immutable origin binding for each copied-content draft: author, action, incoming account and exact revision, INBOX UIDVALIDITY/UID, original creation identity, validated thread context and omission flags. Bind the stable creation request to that exact origin and initial content. A replay must return the existing matching draft without copying again, overwriting edits or creating another draft; a conflicting origin must be refused. Do not take raw source content or threading from posted fields.

Check current Read access to the original mailbox and current Send access to the selected outgoing mailbox before fetching, after network work and atomically when saving. Continue checking the origin's current Read authority/revision on draft detail, list, edit/template use, history and submission detail/prepare/dispatch; Send-only access must not expose copied incoming content after Read revocation. Preserve the existing current-account/session/support restrictions, staff lock, explicit sender review and audit transaction rules. A permission change must not delete stored content or silently rebind the origin.

Add storage through explicit owner-controlled additive preparation. Genuine populated prior draft storage and existing submission records must survive migration, file recovery and reapplication. Preserve old format-1 submission fingerprints and exact MIME bytes; any new format must explicitly bind thread/origin metadata and revalidate it against the saved draft before dispatch. Ordinary drafts retain their original behavior. Reply/Forward buttons only create an editable draft; existing preview/review and explicit Send remain separate, with the same single-attempt and unknown-outcome handling.

## Implemented application layer

`site/app/mail/messages.php` retains raw message bytes only when an internal caller passes the explicit opt-in flag; the default exact-message read returns no raw source, and retained bytes are never persisted, journaled, noticed or rendered. The Reply/Forward actions in `site/admin/controllers/mail_message.php` revalidate the posted route against the open message, resolve an exact creation replay without another mailbox request, then perform one fresh authorized read with retention before `ReplyDraft::prepare` and `mail_reply_drafts_create`. Creating a draft never sends mail.

`site/app/mail/replies.php` stores copied content only in `mail_reply_drafts` behind a content-free `mail_drafts` placeholder (`status=source`, `Copied message draft`, empty recipients/body). `DraftOrigin` binds author, mode, source account/revision, INBOX UIDVALIDITY/UID, the durable successful read identity, initial outgoing account and content hash. Every open, list, save, discard, history, review and dispatch path revalidates current source Read authority and the send grant; revoked access hides copied content without deleting it. `site/database/migrations/mail_replies_migrate.php` is explicit owner-controlled additive setup and refuses unknown or future markers without overwriting them.

`foundation/mail-submission/SubmissionSnapshot.php` accepts optional thread/origin fields; format-1 payloads and fingerprints stay byte-identical and a copied draft cannot prepare through the format-1 path. `PreparedMime.php` emits `In-Reply-To` and `References` for format-2 snapshots only. `site/app/mail/submissions.php` revalidates the saved origin, current source Read authority, read journal, UIDVALIDITY/UID, outgoing account and exact saved content in prepare and again in authorize before any dispatch; replay, prior-attempt and unknown-outcome barriers are unchanged.

`site/admin/views/mail_message.php` renders Reply/Forward controls only after a successful authorized message load, with a sender select limited to current Send grants. `site/admin/views/mail_drafts.php` shows the copied badge, origin/mode and omission notices without exposing raw headers or hidden recipients. `mail_drafts_replies_setup` is an owner-password action; `staff.manage` gates it while reply/forward actions rely on their internal authority checks.
