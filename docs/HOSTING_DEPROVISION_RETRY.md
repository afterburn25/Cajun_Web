# Explicit fenced deletion retry

Unreleased HC-08 work on `codex/hosting-deprovision-retry`, starting from combined PR85 `a9beb6e72208cdfdb7a0ec0f8fe09a7e4883325c`. This adds an internal durable boundary; no route, worker, schema activation, provider request, credential decryption or release version is added.

`hosting_operations_retry_deprovision()` requires the current owner password, active selected client, exact hosting revision and enabled current provider profile revision. Only a retained definite deletion failure explicitly marked retryable qualifies. Pending calls, timeouts, missing confirmation, unsafe failures, active accounts and completed deletion remain refused.

The caller must be the original second approver, with current owner access. The original cancellation requester, distinct approver and explicit data-retention confirmation remain in the immutable canonical journal. Another owner cannot inherit that approval through retry; replacing an unavailable approver requires a separately reviewed workflow. The same provider identity, client, original terms and exact existing resource are retained. A newly reviewed revision of that same provider profile is allowed.

Unlike the local provisioning retry, the canonical deletion retry immediately arms a fresh attempt. Therefore its journal event, immutable dispatch fence and strict audit commit in one transaction under the shared authorization mutex. Only the invocation creating that fence receives a claim. Exact stable-request replay returns null, including after completion or interrupted result persistence. Different action/revision/actor reuse refuses. No saved pending state, restored fence or repeated request authorizes another network call.

Ordinary dispatch input and binding bytes are unchanged. Retry dispatch input has the explicit `command=retry_deprovision` discriminator, derived and rechecked against its canonical event. History validation verifies eligibility and original approver at that precise event prefix, then checks all original and new dispatch/results. Missing original failure or new fence is refused without reconstruction. The generic local-record API still cannot select remote actions.

The existing exact-attempt finalizer records observed reality even after later owner, client or provider access loss. Old results cannot settle the retry; failed result audit retains its unresolved fence. Historical provider-resource ownership remains after deletion. Reconciliation is still a separate unimplemented adapter: raw operator assertions cannot clear unknown outcomes, and canonical negative deletion reconciliation must not be introduced without its own atomic-fence policy.

Prepared PHP8.2/8.4 native MariaDB cases cover approval/retention history, stable replay and action separation, concurrent requests, access changes while waiting, profile changes, strict event/fence/result audit rollback, exact late results, restart, missing/tampered proof and resource retention.
