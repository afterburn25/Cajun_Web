## Application contract

- Add a separate planning section to the existing admin project page and client workspace. Preserve project title/summary/seven stages/free-text milestones, approvals, conversation, invoices, private files and website deliveries. Scope, contact label, calendar target date, client action, blockers and structured milestones use the existing native planning API. No invented progress percentages, automatic deadline promises or contact login privileges.
- `project_planning_setup` is owner-only, current-password, backup-confirmed and CSRF protected in Version & database. No automatic migration. Unknown schema markers or retained unactivated planning rows refuse editing; no fallback may overwrite them.
- `project_planning_save` requires current `clients.manage`, no support context, CSRF and the existing native atomic save. Capture bounded raw form values before validation. Fields: positive `id`/`client_id`, 32-hex `request_id`, 64-hex `expected`, scope/contact/date/client_action/blockers and canonical `milestones_json` (at most 262144 bytes). Parse exact canonical JSON with bounded depth before `ProjectPlan::fromArray`. Do not normalize exact submitted text. Non-string, oversized or invalid UTF-8 values are explicitly not retained.
- Retain original expected version/request and safe unsaved fields after validation/stale failures. Show current saved plan separately and an explicit reload link. Never silently adopt a newer version. A retry of an original successful request goes to its original event and cannot revert later changes.
- Progressive enhancement uses one serialized milestone field, avoiding hundreds of named dependency inputs and shared-host `max_input_vars` truncation. Visible controls edit one selected milestone at a time: title, details, status, studio/client responsibility, optional calendar date and up to eight prerequisites. Add new random identities, reorder, cancel saved milestones; remove only unsaved milestones. Retained IDs cannot disappear. Dependencies remain sorted, unique and local; server enforces graph/completion rules. DOM text APIs escape user content. Without JavaScript, ordinary plan fields remain usable and existing milestone bytes remain unchanged; clearly explain that milestone editing requires JavaScript.
- Client workspace is read-only for planning. Display current scope/contact/date/actions/blockers and ordered milestone details/status/responsibility/dependency names. Reuse explicit current client or scoped support authorization; support reads retain real staff attribution. No client planning-write action.
- History shows ten revisions per page, newest first within the selected chronological page. `plan_page` accepts 0..410; `focus_plan` is empty or 32 lowercase hex. A foreign event refuses. Exact anchors are `planning-<event-id>`. Show the real UTC recording time, changed-field labels and an expandable saved snapshot. Initial event says Plan created, with no reconstructed older history.

## Personal activity contract

Both initial and later saved plans project `planning:<event-id>` into existing private workspace activity. Staff exclude their own saves; clients require exact current project ownership. Use revision as the same-second sequence and exact `focus_plan` destination. No email dispatch. Read/count/page/cursor/destination/mark operations revalidate complete bounded planning history, current authority, event metadata and head under the existing staff mutex/transaction. Cache validated project identities, not entire large histories. Preserve passive idle expiry and individual read/unread state. Activity failure cannot roll back or duplicate a saved plan.
