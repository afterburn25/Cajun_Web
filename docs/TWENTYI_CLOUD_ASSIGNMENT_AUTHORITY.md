## Owner workflow

An owner prepares cloud assignment history with their current password. Preparation preserves existing cloud reads, assignments and events. It cannot establish which encrypted credential originally produced a legacy read from an account revision or saved fingerprint alone. Imported assignments therefore retain their records but require a new protected cloud inventory read and explicit owner reapproval before server details are shared under the current connection.

New approvals require the latest cloud read for the selected account to be complete, to contain the exact server, and to be no more than fifteen minutes old. Failed, unfinished and partial later attempts prevent fallback to an earlier successful read. Sequence and independently retained start-audit order must agree. Profile revision, sealed credential identity, key fingerprint and exact original client/assignment are checked again before a dependent operation is admitted.

Reapproval and unlinking require current owner authority and password. Stale forms cannot overwrite a later assignment or approve another client's server. Original owner revocation or changed authentication prevents current control authority; it does not silently rewrite saved assignment history. These are local permission changes and do not alter the provider's cloud server.

## Client display

Before history preparation, an authenticated active client with an existing cloud assignment receives a review-required state without cloud facts. The services page explains that the studio needs to review the saved assignment instead of saying no service is linked. A genuinely unassigned client retains the ordinary empty state. A legacy revision or retained fingerprint cannot establish which credential originally produced those facts, even if saved encrypted bytes are later restored. Preparation preserves the assignment record, and a fresh protected read plus explicit owner reapproval establishes the sharing context. No status read prepares history or opens the provider credential.

A signed-in client can see only the server explicitly assigned to that client. Its authenticated identity and active account row are checked again inside the same guarded inspection before assignment existence or facts are read. The projection excludes sibling package identifiers and account credentials. A fresh valid observation is distinguished from historical specifications. Later failed or partial reads can retain previously shared historical facts under the same approved account context; they cannot make those facts current permission for a new action.

When the server is absent from the latest saved observation, the view says so without asserting deletion. A changed account revision or encrypted credential context hides the earlier account's facts. Missing or corrupted protected history produces a recovery message and no approval controls. Client and owner page reads perform no setup, credential decryption or provider request.

The display does not claim server health, website placement, billing activation, TLS health, console access or SSH access. Existing cloud website creation and package confirmation retain their separate request/result boundaries.

## Durable evidence and recovery

The new `provider_cloud_assignment_evidence` table retains immutable start, finish and assignment-event documents. Each canonical document binds physical indexes, original source bytes, its exact audit, previous evidence hash and keyed proof. An independent authenticated settings head binds preparation, count and tail. Every retained row is validated before indexed authority queries, using bounded-memory pages with an unconditional first page. Original common refresh and all cloud link/relink/unlink audits are also reconciled.

Shared refresh hooks append evidence inside the existing intent/result transaction and staff mutex. Assignment, event, audit and authenticated head updates share one transaction. The existing single refresh executor, quotas, thirty-second cooldown and network boundary remain. A failed witness write rolls back the local transaction; an interrupted read remains an unfinished intent that cannot authorize a later action.

Ordinary reads never recreate established evidence. Missing rows, changed canonical indexes, paired losses, reordered source sequences or absent preparation evidence require restoration of the original database history. Preparation is idempotent only when the existing protected history is intact. It does not repair corrupted records or turn an imported read into a newly approved observation.
