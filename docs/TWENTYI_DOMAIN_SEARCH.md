## Primary evidence and exact contract

[20i API documentation](https://docs.20i.com/api/20i-api-documentation) describes the domain-search NDJSON stream, unordered suggestions and checked responses, lack of TLD selection and possible 24-hour blocking. Its [official console example](https://docs.20i.com/assets/images/ee/support/3_Reseller_hosting_API_responses_example.jpg), inspected on 2026-10-15, shows `[{"header":{"names":["testdomainsearch20i.com"]}},{"name":"testdomainsearch20i.com","can":"register"}]`. The selected owner handoff confirms `GET /domain-search/{prefix_or_name}`; this implementation deliberately accepts only one fully qualified ASCII name.

The request uses the existing exact HTTPS host, pinned validated public destination, TLS verification, no redirects/proxies, bounded transfer and one credential resolution. Parser bounds: 262,144 response bytes, 4,096 bytes per packet, 256 records, depth 8 and 15 seconds. IDN/punycode, URL syntax and bulk input are refused. Suggestions are never reported as available without their own complete exact-name lookup. Unknown availability markers do not establish that a domain is unavailable: they remain unverified.

The authenticated live read is not enabled in an application route by this checkpoint. A UI must persist intent before networking, recheck current account/revision/actor authority before and after the request, maintain shared limits and provider backoff across workers, retain honest partial/error history, filter unsold TLDs locally and distinguish historical availability from a current quote or reservation. Client/public exposure, retail pricing, eligible periods, registration and transfers need their own tests and authorization. Search success must never grant an ownership link or a registrar action.
