## Content contract

- One selected mailbox determines the From identity. No arbitrary From, Reply-To, envelope sender or transport header input. The initial form accepts comma-separated bare addresses; CR/LF and empty comma segments are refused, not trimmed into valid headers. Subject/body whitespace is preserved, with only the documented body newline normalization. Recipients use To/Cc/Bcc lists of bare ASCII email addresses; display names, comments, quoted local parts, domain literals and internationalized addresses are outside this first input contract. Domain case is normalized; local-part bytes are preserved.
- At most 20 recipients total. Lists must be dense lists of strings, not maps or implicitly cast values. Trim surrounding ordinary spaces only; reject CR/LF, tabs, controls, invalid addresses and addresses longer than 254 bytes. Refuse duplicate normalized addresses across all three lists rather than silently moving a Bcc recipient into a visible header. Case-sensitive local parts remain distinct because provider equivalence has not been established.
- Draft subject is valid UTF-8 plain text, at most 200 bytes, with no ASCII controls including tabs or line breaks. Body is valid UTF-8 plain text, at most 20,000 bytes after CRLF/CR-to-LF normalization, allowing tabs and LF but no other ASCII controls. Empty recipients, subject and body are valid for an unfinished draft; this is not permission or readiness to send.
- HTML-looking text stays literal. Never evaluate code, execute links, load remote images or treat draft body text as trusted HTML. Views must escape every field, including textarea closing-tag payloads.
- Template insertion reuses `EmailTemplate::insertableBy()` and `preview()`. Only active, nontransactional templates visible to the current actor are eligible. Missing values prevent insertion. Values are resolved in a single pass and then subject/body limits are independently checked; CR/LF injected through a subject placeholder must fail. Inserted plaintext is a snapshot that the author can edit. Later template changes cannot silently alter a saved draft. Literal brace text inside an explicit replacement remains literal and is not recursively expanded.

## Application authority and persistence contract (78 native checks per runtime verified at 2748030)

Reuse existing sessions, current `mail.send` permission and the exact mailbox Send assignment, including for owners. Support/client/anonymous sessions are denied. Staff may access only drafts they authored; owning the site does not imply reading another staff member's private drafts. Revoked/expired grants and disabled accounts remove draft access immediately without deleting content. The selected mailbox and saved profile revision are explicit in forms; changed sender settings require a fresh review and must not silently retarget a draft. No inference from matching recipient addresses to client records.

Owner-password-confirmed additive setup uses the existing migration, staff-lock and transaction conventions. Use a separate additive local draft table with an opaque random id, author id, mailbox id, acknowledged mailbox revision, draft revision, retained status, plaintext To/Cc/Bcc/subject/body and timestamps. These are private business records in the configured database, like existing project messages; they are not public assets or automatically encrypted mail credential values. Keep content out of audit/diagnostics, URLs, bells, exports and release evidence. No body history copy is required merely to edit a draft; metadata audit records id, revision and action. State transitions and strict audit commit together. Discard is a retained local state, never a remote mailbox deletion.

CSRF protects all changes and previews. Current authority and optimistic revisions are checked again inside the shared staff lock before writes. Repeated create submissions need a stable form token/id and an exact saved-payload replay rule so lost responses do not duplicate drafts; stale edits must preserve entered values while reporting a conflict. Account switching requires explicit current Send access on the destination, a new saved account revision, and a new draft revision. Avoid cross-account or cross-author content exposure through errors or history.

Template insertion additionally requires the existing `mail.templates.manage` capability and current shared/personal visibility; do not add a second permission system. Fetch the exact active template revision under current authority, use explicit manually entered sample fields plus the canonical portal URL, and copy the rendered subject/body only after content validation. No unrestricted client/project lookup, transactional receipt/reset template or privileged business transition is implied.
