## Native agreement

Deploy exact mirrors of the existing calendar, terms and lifecycle classes. Store their canonical initial/current documents and hash-linked retained events using additive owner-password setup. Existing installations gain no inferred terms or consent. Verify exact schema, indexes, collations and restrictive relationships, refusing unknown versions or populated unrecognized tables. Setup never deletes customer records.

Staff need current client-management and payment-management permissions outside support, with current client/project ownership. Clients need their own unexpired, active session outside support and explicit confirmation for accept, decline or end. Staff cannot record client acceptance. Reads and retries recheck current authority. Public PHP entry points never accept caller timestamps or SQL/table identifiers. No routes or HTTP forms are included until their separately tested interface increment.

Each schedule belongs to one existing service subscription and one project owned by its client. Before first offer, validate the complete current subscription/plan histories, require an active subscription, and pin its exact current revision/hash. Amount/currency/cadence must equal the retained subscribed plan; alternate financial terms require a new agreed source. Later source history is fully verified; new acceptance, activation, resumption and invoice issuance require the source still active. Historical terms and issued invoices remain inspectable after a legitimate service pause/cancellation. Decline, withdrawal, pause and end must remain possible even when the source is no longer active. Source-history corruption always refuses.

Use a durable per-subscription head, a unique `(subscription_id, generation)` and a bounded sequence of at most 256 schedules. Record exact preceding schedule/hash in each creation request. A new offer requires the predecessor's exact reviewed state and terminal decline/withdrawal/end. Ended predecessors may still cover earlier periods: replacement terms must retain the timezone and start no earlier than the prior end boundary. Verify the entire sequence and latest head before mutations. This permits future replacement while preventing overlapping charges. Shared application lock plus transaction, source-row lock and unique constraints serialize independent workers. Every changed record and minimal audit must commit together.

For each schedule retain at most 256 exact lifecycle events, with current expected revision, actor, original timestamp, canonical command input and before/after hashes. Reconstruct and compare all events with the current document before reading or changing it. Same-ID exact-command retries return the retained result after current authorization; conflicting IDs or stale revisions refuse. Changes use server time and the existing future-whole-period policy. Reserve the final termination slot. Terms are immutable; changes require a new offer and fresh client consent.

## Period invoices

An explicitly authorized staff action creates one existing `studio_invoices` record for an eligible positive-price period. Reuse the current ledger and payment request flow. Permanent unique `(schedule_id, period_index)` and unique invoice/request IDs prevent duplicate obligations, including concurrent requests. Retain the exact schedule prefix, period dates/timezone/due date/amount, source binding, invoice snapshot, actor, server issue time and request fingerprint. Validate current history and source authority before new issuance; exact replay returns the original invoice without changing payment state. Changed request contents refuse. No caller-supplied amount or automatic payment is accepted.

Before existing ledger balance/receipt/payment-request use, validate the recurring invoice's retained mapping, lifecycle consent/eligibility at issuance, exact historical schedule prefix and unchanged invoice identity/financial fields. Historical invoice validity must not depend on the source still being active today. Refuse missing/extra/tampered mappings, altered terms, foreign client/project, changed amount/dates or malformed retained histories. Existing non-recurring and design-stage invoices keep their own guards. Invoice insertion, permanent mapping and audit are atomic; failures roll back all three. Zero-price periods create no invoice or fabricated receipt.
