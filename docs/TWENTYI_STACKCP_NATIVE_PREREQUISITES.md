# Proposed native prerequisites for StackCP support handoff

This is an implementation proposal from frozen556, not executable setup, approved shared wiring or provider acceptance. The [pure contract](TWENTYI_STACKCP_HANDOFF_CONTRACT.md) is the current implemented scope. Review this design before adding schema, shared credentials, routers, transport or workflows.

## Distinct protected authentication configuration

Add dedicated owner-only configuration for an OAuth **client key**, separate from the existing profile's General API key. Do not reuse the existing key, decode a Combined API Key without its contract, store credentials in URLs or accept per-request hosts. Reuse `provider_settings_vault_key()` and its unchanged private-root/0600 requirements; use a distinct AES-GCM associated-data domain binding installation prefix, provider profile, auth record ID, revision and environment. Existing ciphertext and its context must remain unchanged.

Proposed dedicated files are `site/app/providers/stackcp_auth.php`, `stackcp_auth_storage.php`, `site/database/schema/provider_stackcp_auth_schema.php`, and focused native tests. An append-only auth revision record would hold ciphertext, enabled status, original owner/auth version and creation metadata. Retained count/audit/HMAC and indexed-document checks must detect missing/restored/moved history before a current revision is selected. Never let a marker reset silently recreate established key/history. No raw key or raw-key-derived value appears in a public page or general audit.

Preparation/save/disable uses current owner password, CSRF, the existing staff mutex and owned transaction. Support impersonation, a client session and delegated `support.login` alone are refused. Forms bind the exact observed profile/auth revisions and preserve safe fields after errors; key/password fields are never redisplayed. Rotation or disable invalidates future launch approvals. Ordinary GETs render stored safe metadata only and neither open the vault nor repair storage. Public status says configured/disabled/unavailable, not provider verified. The initial native prerequisite need not call the provider at all.

## Explicit Stack-user/resource assignment

Add an independent local owner-reviewed association between a current explicitly assigned hosting package/client and a selected Stack-user identity. Do not choose the first returned user, infer ownership from a matching email/name, create/change a provider user, or borrow PHP-version observation authority. A manual identity can be saved as an unverified draft; it cannot authorize token issuance.

Before enabling a future launch, the owner must obtain successful typed membership and whole-grant observations from the exact current account/key. The former requires an object entry with exact `identity`; the latter has a documented object-tuple list. Preserve independent common intent/outcome/audit/count witnesses, sequence-first latest-state checks and exact profile/key/source binding. Failed or unfinished latest reads must invalidate earlier eligible snapshots; altered sequence, paired history loss and current link/owner/key changes must refuse before secrets or network. The complete response types, error semantics and own quota/cooldown use must be reviewed before wiring these reads into the common executor.

Initial admission accepts only a single known package grant for the selected identity and rejects every additional/unknown/server/domain grant. Present this as an observed grant list for a **StackCP user**, never a package-only session. It cannot atomically constrain remote state after the read. A broader multi-resource implementation must explicitly validate every resource against current ownership and obtain separate owner approval; no wildcard allowance is inferred.

Proposed dedicated files are `stackcp_assignments.php`, `stackcp_assignment_storage.php`, `provider_stackcp_assignment_schema.php` and focused tests. Bind immutable revision documents to actor/client versions, original/current package link/audit/source, general profile revision/key, separate auth revision/ciphertext, exact membership/grant source and local support policy. Keep one current local association without erasing earlier revisions. Independent lookup-index/HMAC/count/audit validation must precede indexed admission.

## Shared interfaces requiring separate review

The initial owner configuration and draft-assignment module can be tested without provider calls. Its exact proposed router/import/view/schema/private-path/installer patch must be reviewed before application. Preserve current provider operations, support identity, client read-only paths, all existing fixture owners and scheduler-last test order. Run the appropriate synthetic native matrix only after source/fixtures are reviewed.

A later executable handoff additionally needs:

1. Current owner and allowed-client policy checks outside impersonated support, explicit provider-access consent and a short local launch approval bound to every current revision. Delegated support is outside the initial scope; existing website support permissions confer no provider privilege.
2. Durable one-use admission under the real shared mutex, exact request/phase witnesses and no transaction around the network. Treat both POST token/session creation and the final session-bearing browser GET as access effects. A crash/lost response cannot be retried merely because a local token was not saved. No raw token/session/URL may enter a generic operation ledger or saved observation.
3. The existing HTTP abstraction with separately reviewed exact allowlists for `api.20i.com:443`, `auth-api.20i.com:3000` and `www.stackcp.com:443`, correct credential role per phase, public-DNS pinning, strict TLS, redirects disabled, no reusable cookies and current-authority callbacks before/after transport. This does not authorize a generic endpoint client or actual port probe.
4. An evidenced brand-response/default-destination policy. The old SDK's custom HTTP destination must be refused. Do not rewrite a provider-selected custom brand to the default host or fabricate an empty brand object without an evidenced contract. The pure descriptor does not solve that missing schema.
5. Ephemeral server-side delivery with explicit no-store/referrer protection and safe finite errors; safe audits record identity/phase/outcome only. Browser headers/history necessarily receive the provider bearer URL when that future action is executed; access-log redaction and disclosure behavior require explicit testing. A local approval expiring or being revoked only stops future use of local authority, not provider sessions already created.
6. Exact provider account/operation acceptance and a documented response/recovery contract. `expires_in` presence alone proves no session lifetime, and neither remote session revocation nor atomic package restriction is evidenced. These remain explicit product limits. The entire provider-support/SSH roadmap remains incomplete.

Meaningful native prerequisites include fresh/prepared/unknown/missing-family storage, supported credential rotation/restoration, wrong-role/support/client refusal, current-owner revocation while waiting for the mutex, transaction/audit rollback, stale captured configuration/assignment forms, cross-client relink, original-index tampering, retained-count loss and no secret resolution during GETs. Subsequent actual browser cases must use their own activated owner and preserve inherited histories/budgets; no history timestamps or production limits may be rewritten to make fixtures pass.
