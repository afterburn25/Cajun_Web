## Exact additive schema

All tables use InnoDB. Local project/client/staff IDs and revision are INT UNSIGNED. Opaque IDs are CHAR(32) ascii_bin, SHA256 values CHAR(64) ascii_bin, canonical JSON LONGTEXT utf8mb4_bin. No defaults, generated columns or extra indexes are accepted. All foreign keys use RESTRICT/NO ACTION on delete/update. Exact column order/types/nullability/collations, primary/unique/ordinary indexes and relationships are validated during preparation; unknown existing/populated tables are not adopted.

| Table | Ordered fields | Keys and relationships |
|---|---|---|
| `studio_plan_events` | id, job_id, client_id, staff_id, revision, kind (VARCHAR20 ascii_bin), created_at (DATETIME), event_json, event_sha256; all NOT NULL | PRIMARY(id); UNIQUE job_revision(job_id,revision); INDEX client_updates(client_id,created_at,id); INDEX staff_id(staff_id); job_id → studio_jobs.id, client_id → studio_clients.id, staff_id → users.id |
| `studio_plan_requests` | id, input_json, input_sha256; all NOT NULL | PRIMARY(id); id → studio_plan_events.id |
| `studio_plan_heads` | id (INT UNSIGNED), event_id, event_sha256, revision, plan_json, plan_sha256, retained_bytes (BIGINT UNSIGNED); all NOT NULL | PRIMARY(id); UNIQUE head_event(event_id); id → studio_jobs.id, event_id → studio_plan_events.id |

The head is an independent anchor plus the current exact plan, never a substitute for validating retained history. It catches missing history even when a later plan reverts to earlier values. Every saved event has exactly one request; there is no synthetic adoption event. The initial plan is revision0 and honestly records the first explicit planning save.

`project_planning_migrate(password)` runs under the existing staff mutex, refuses inherited transactions, support context, non-owner or stale/disabled identity, and requires the current owner password plus current staff-management authority. Only empty or version1 storage is recognized. Create missing tables additively and validate all three before an atomic version/audit transaction sets `project_planning_schema_version=1`. Missing markers with existing records fail closed. Setup failures preserve existing rows. No fresh-install or ordinary-read path automatically prepares planning. Later HTTP setup additionally requires CSRF and explicit owner action.

## Native API and authority

- `project_planning_save(jobId, clientId, requestId, expected, fields)` accepts only an existing currently owned project and active client. Current `clients.manage` staff authority is rechecked after acquiring the shared staff mutex, then all business writes use one transaction. Support and client sessions cannot invoke the staff write. Canonical fields must satisfy the complete pure plan/dependency contract. Request IDs are lowercase32-hex; expected versions are lowercase64-hex.
- `project_planning_staff_get(jobId, page=0, focus='', touch=true)` requires current permitted staff and may inspect an inactive client's retained history. It returns the current plan, bounded dated page, current expected version and client ID. It performs no setup or save.
- `project_planning_client_get(jobId, clientId, page=0, focus='', support=null, touch=true)` requires current active client identity, matching authentication version, existing idle/absolute lifetime and exact current ownership, or an explicit current scoped support session. Clients cannot choose another authenticated client by parameter. Support receives only the public projection; active reads preserve real staff attribution and audit atomically. Passive reads preserve idle timestamps and audit state.
- Internal helpers live in `site/app/projects/planning.php` and `planning_history.php`; schema/migration live under the existing protected database directories. For an unplanned project, expected is SHA256 of exact canonical JSON with ordered fields `format:1, project_id, client_id, head:null`. It does not invent a legacy plan or depend on unrelated free-text edits. After the first save, expected is the current complete event fingerprint. A changed current client/project relationship invalidates both reads and writes; prior history is never reassigned implicitly.

## Atomic history and original request replay

The exact request JSON has ordered fields `format:1, project_id, client_id, staff_id, expected, fields`. Its identity equals its event ID and its SHA256 is retained. A save atomically appends event+request, inserts/updates the head/current plan/retained byte count, and writes a content-free audit entry with actor/project/event IDs. It does not change existing free-text project fields or create invoices, payments, notices or provider operations.

An exact original request can be retried after later changes: recheck current authority/client/ownership and validate the complete current chain before returning `{job_id,event_id,replayed:true}`. It returns the earlier event identity without restoring its old plan, appending an event or duplicating audit. Changing actor, job, client, expected token or accepted fields under the same request ID refuses. Stale new requests and unchanged plans refuse without mutation. Retain cancelled milestone identities. Database/audit failure rolls back all writes; competing saves under the shared lock cannot both use one stale version.

## Complete validation, bounded memory and pagination

Retain up to4,096 events and32MiB of combined event/request JSON per project. These are safe processing/storage limits, not automatic purging. At capacity refuse a new save and preserve all existing data; reads and exact original retries remain available. Sum byte lengths and count before reading payloads, reject oversized/corrupt storage without allocating an unbounded history, and validate one event at a time against its predecessor. Do not retain every decoded event in memory. A display page contains at most10 events; page0 means the newest page. A focused event must belong to the current project and resolves its exact retained page. Out-of-range/invalid pages or another project's focus refuse.

Validation checks the entire ordered retained chain, unique event identities, zero-based contiguous revisions, exact project/client/staff/time/kind columns, canonical event/hash, exact reconstructed request bytes/hash, pure dependency/retained-ID rules, previous complete event fingerprint, current head ID/hash/revision/byte count and exact current plan/hash. No-op corruption, middle/tail/head loss, mismatched ownership, request corruption and A→B→A truncation must refuse before any projection or replay. Current client views omit internal staff/project/client/hash/request/head metadata while preserving the actual public plan/history. Notification integration must later validate this same history before exposing or counting events.
