## Application candidate and owner workflow

Fresh installations create empty request tables. On an upgraded site, an owner opens **Email accounts**, enters their current password and selects **Prepare inbox reading**. This verifies/adds the two request tables and readiness flag without connecting to any server or changing saved credentials. Unknown existing records, incompatible columns/collations or foreign keys are refused; audit failure leaves setup unready. Existing configured account secrets and their private key remain unchanged.

Each staff member needs current global `mail.read` and an active read assignment to the selected enabled account, including owners. **My email accounts → Open inbox → Load recent headers** makes the explicit request. GET navigation does not connect. Requests require CSRF and the current saved revision, allow at most one attempt per account per 15 seconds and 120 per staff hour, and preserve every started attempt even if DNS/network work fails. No automatic refresh. The page displays newest-first sender, subject, provider date and read status as escaped text; long normalized fields are labeled shortened. Only a proven empty mailbox displays empty success. Failed or incomplete batches display no partial headers.

DNS runs after committed intent and outside the staff lock. Credential use is serialized with account/grant edits and holds no InnoDB transaction. Authority is refreshed after DNS, at receiving boundaries and before rendering. Started and separate immutable terminal records each require strict audit; a failed terminal commit returns no headers. Only identifiers, saved revisions, timestamps, outcomes, elapsed time, counts and UIDVALIDITY persist. Headers are neither stored nor cached in the session, and the response sends no-store/private and no-referrer. Request history is scoped to the current staff identity and mailbox grant.

The builder verifies canonical dependency/license hashes and all 2,078 runtime mirror files before packaging. Effective access denial for library source and Composer metadata is checked with Apache; the PHP development server alone is not protection evidence. Native authorization/concurrency and packaged synthetic TLS/HTTP/Chromium fixtures are added, together with retained-history/key recovery from the actual 1.16.0 package. These new application checks are pending. Foundation exact-head `8ad1d01` already passed 548 named checks on each PHP 8.2/8.4 runner in [38471766759](https://github.com/afterburn25/Cajun_Web/actions/runs/38471766759), including fresh lock-only byte reproduction. ## First receiving boundary

An explicitly authorized staff member requests the newest bounded batch of INBOX header summaries for one saved account. Reuse current global `mail.read`, active per-mailbox assignment, enabled saved revision, current session/support restrictions and the existing private credential key. Even owners need an assignment. Refresh authority after DNS, immediately before credentials and before presenting data. Serialize credential use with account/grant changes; do not hold an InnoDB transaction over network work. Rate limits and strict access auditing belong in the application adapter before any usable release.

Use verified public destination resolution/pinning and original-host TLS identity from the released policy. Support incoming 993/TLS and 143/mandatory STARTTLS without alternative CA, private-network, proxy or arbitrary command settings. Keep a separate bounded receiving stream and maintained parser adapter. No library logger, remote exception or authentication payload may reach UI, audit or application logs. A failed/partial batch must not appear as an empty successful inbox.

Read with EXAMINE and BODY.PEEK, never SELECT, STORE, APPEND, EXPUNGE or send commands. Start with at most 20 newest sequence positions in the captured EXISTS range; return immutable account/folder/UIDVALIDITY/UID identities and reject duplicate/out-of-range identities. Preserve the UID boundary before later message links. No unbounded SEARCH ALL/UNSEEN or fetch-all convenience API. Concurrent mailbox changes may require refresh; this is not a persistent synchronization cursor. Folders beyond INBOX and background polling remain separate work.

Header-only literals are capped at 16 KiB each, total received bytes/tokens/lines and request duration are bounded, and parser nesting is capped before recursion. A per-message body size is metadata only; no whole body or attachment is downloaded in this boundary. Decode bounded header text with the maintained MIME library, normalize controls and output escaped text. Subjects, sender labels and provider dates remain untrusted claims. No remote images, HTML rendering, executable attachments, automatic read flags or message deletion.

This is the receiving foundation, not a declaration that full webmail is finished. A useful application release still requires its scoped staff interface, rate/access audit behavior, sanitized failures, actual permission/database/HTTP/TLS/upgrade acceptance and explicit inbox limitations. Message bodies, attachments, compose/send, OAuth and exact-message bells follow their own contracts.

## Implemented receiving foundation (not yet deployed)

`InboxReader` accepts an already validated public DNS address and a mandatory current-authorization callback. It creates `ReceivingStream` with the original hostname, numeric destination and fixed supported incoming port/encryption. TLS identity checks, SNI and TLS 1.2/1.3 are mandatory. No production connector, CA, proxy or resolver override is offered. The stream cannot reopen, change timeouts or disable TLS. Limits: 5-second connect/per-I/O, 20-second total after DNS, 393,216 received bytes, 256 protocol lines of at most 8,192 bytes, 16 writes/8,192 sent bytes; literal reads are exact despite fragmented TLS records. STARTTLS rejects buffered plaintext and requires a complete maintained-parser boundary.

`HeaderSession` exposes only the fixed read-only operation, using the maintained parser with 4,096 aggregate tokens, nesting 12 and strict 16 KiB header literals. It verifies a normal greeting, refreshed post-TLS capabilities and AUTH=PLAIN, and checks current authority before credentials, after authentication, before fetching and before returning data. The production entry checks authority before connecting as well. It requires EXAMINE with READ-ONLY, one UIDVALIDITY and one captured EXISTS count; fetches only the newest at most 20 sequence positions; preserves UIDVALIDITY/UID as validated unsigned-32-bit text and rejects duplicate, missing or out-of-range replies. Concurrent mailbox changes require refresh, never a fabricated empty inbox. Only a proven zero EXISTS count is an empty result.

`HeaderDecoder` accepts at most 128 physical header lines and 4,096 bytes per unfolded field. It discards body/MIME directives, parses only Subject/From/Date with an instance-local NullLogger and no global MIME definitions/plugins, caps header tokens/comments, and refuses MIME parse errors. It normalizes controls/bidi format characters and clips displayed claims to 1,000 UTF-8 bytes with an explicit headers_truncated flag. Markup remains untrusted text for the future UI to escape. No body, attachment, remote image, flag mutation or outgoing message is supported.
