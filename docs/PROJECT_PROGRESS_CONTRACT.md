## Pure record contract

A snapshot is an ordered object: `title`, `summary`, `stage`, `milestones`. All values are exact UTF-8 text. Title is nonblank, single-line, at most160 bytes; summary at most10,000 bytes; milestones at most15,000 bytes. Empty summary/milestones are allowed. Multiline text permits LF, CRLF, CR and tab but no NUL or other control characters. Preserve exact stored newline bytes: the actual existing `posted()` helper retains CRLF/CR in project descriptions. New history must accept these existing records without silent normalization. Single-line title/stage still refuse every control character. Stage is one existing key: `discovery`, `design`, `development`, `review`, `launched`, `care`, `paused`. Unknown/missing/extra fields, non-text values, invalid UTF-8 and oversized values are rejected. Raw text remains text; views must escape it. These limits match the existing bounded form and do not silently truncate stored values.

An immutable event contains ordered `format`, `id`, `project_id`, `client_id`, `revision`, `kind`, `staff_id`, `occurred_at`, `before_sha256`, `before`, `after`, `changed_fields`. IDs are lowercase32-hex. Local project/client/staff IDs are positive integers up to2,147,483,647. UTC epoch time is an integer from0 through253,402,300,799. Revision is0 for a baseline, otherwise a positive integer up to2,147,483,647. Canonical compact JSON is bounded to262,144 bytes and its SHA256 identifies the exact event. Unknown JSON keys, duplicate keys, noncanonical encodings/order and invalid types are refused.

`tracking_started` is a revision0 snapshot of what was actually present when tracking began; before/hash are null and changed fields are empty. It never claims a historical stage transition. `updated` retains complete before/after public snapshots, the preceding event fingerprint and exactly the changed field names in snapshot order. It requires at least one real difference. Updates preserve project/client identity, increase revision by one and never precede the previous timestamp. Same-second updates retain their revision order. A caller must supply the exact previous fingerprint; stale and duplicate event IDs are rejected. Cross-event linkage must be validated against the previous event, not inferred from a valid standalone JSON object. `verifyChain` validates1–100 consecutive events against a baseline or supplied predecessor, including unique identities within that page. Native unique constraints must also prevent duplicate IDs across pages; a bounded page is not proof of the entire retained database.

The pure client projection validates the stored client ID, omits internal staff/hash metadata and exposes public snapshots and dated changes. It is only a projection: the native adapter must separately enforce current ownership and access. Private notes do not belong in this record. They remain in the private ticket flow.

## Native persistence and authorization contract

Owner-confirmed additive setup must validate exact schema, indexes and restrictive relationships; unknown versions or incompatible/populated unrecognized tables are refused without deleting data. Preparation does not manufacture past history. Existing projects gain an honest baseline when first changed after preparation; the baseline and update are one transaction. New projects start with a baseline at creation. Earlier state that cannot satisfy the inspected contract must be reported, never silently repaired or truncated.

Use append-only `studio_progress_events`, linked to the existing project/client/staff rows, unique `(job_id,revision)` and unique request/event identity. Retain the exact submitted request fingerprint separately from the event-chain fingerprint: the first edit of an untracked project has a snapshot-based form token, whereas later edits have a history-head token. A request binds real staff, current project/client, original expected token and exact accepted public fields. Replaying the original request after later updates returns the existing result without another write; changed payload, actor or ownership is refused. Revalidate current access before accepting any replay.

The protected write requires current `clients.manage`, active current client, staff session validation and no support context. Acquire the existing shared staff/account mutex and project row lock, recheck authority after waiting, validate the retained history and current project projection, check the original form token, then atomically update the existing row, append events and write a content-free audit record. Failure rolls back all three. No direct prepared `studio_job` write may bypass history. Stale forms preserve exact bounded unsaved text, original expected token and request ID; a rejected retry cannot silently overwrite another editor's update. Unprepared legacy behavior remains explicit until owner setup is complete.

Client reads resolve current project ownership, active account and current authentication; another client's identifier never grants access. Support reads require the current scoped support session and preserve real staff attribution. Support cannot change progress or mark the client's activity read. Staff reads require the current project permission. No mailbox or 20i permission is implied. Passive notification checks preserve idle-session expiry.

## Native storage increment — precise adapter contract

Branch `codex/project-progress-storage` starts at frozen3677ccf, with155 local record checks per mode; its exact GitHub correction matrix is pending when this native contract is recorded. Codex owns the protected `site/app/projects/progress.php`, schema/migration, exact private foundation mirrors, isolated native fixture/workflow and installer inventory wiring. No route, automatic setup, project-editor bypass, activity item or UI is activated in this storage-only increment. Existing shipping behavior remains unprepared until the later complete integration.

Three additive tables extend existing identities. `studio_progress_events` stores `id` (32-hex primary key), `job_id`, `client_id`, `staff_id`, `revision`, `kind`, `created_at` (UTC), canonical `event_json` and `event_sha256`; unique `(job_id,revision)` and restrictive foreign keys preserve the existing project/client/staff. `studio_progress_requests` extends the final event by the same primary-key/FK `id`, canonical `input_json` and `input_sha256`. `studio_progress_heads` stores the existing project ID as primary key, current event ID (unique restrictive FK), exact current event hash and revision. This independent head anchor must agree with the full retained event/request chain and current project projection. There is no parallel project table or automatic deletion. Every saved request binds format1, create/update command, originally submitted project ID (zero for creation), client, actual staff, original expected token and exact accepted fields.

New projects require an empty expected token and append a request-linked baseline. A previously untracked project's token hashes a versioned envelope of actual project/client identity, exact current snapshot and null history head. Its first real change appends an honest baseline and request-linked update atomically; the baseline has no separate user request, the same actual staff/time as that first update, and a distinct generated ID. Subsequent edits expect the prior event fingerprint. No-op saves are refused without writing. Exact retries after newer updates find the original request, validate current authority/ownership and the complete retained history, then return its existing project/event without replacing current values. Another actor, changed payload or changed original expected token cannot reuse the request.

Validate every retained event and request, their canonical hashes and SQL projections, contiguous revisions, baseline/request pattern, exact earlier snapshots and current `studio_jobs` fields. Stream batches of at most100 events, with a documented4,096-event per-project bound to keep validation finite on shared hosting. Capacity refuses new writes while preserving current records; it does not prune history. Reads return at most30 displayed events and resolve exact focus IDs to their actual page; a page request cannot relax current authorization or full-history validation. Native current staff uses `clients.manage`; current authenticated clients read only their own active project. A scoped current support session may read the client projection with real staff attribution and a content-free support audit, but cannot write progress or client read state. Passive reads preserve idle timestamps. Owner-password preparation validates exact table shapes/indexes/relationships, refuses unknown versions or unrecognized populated tables, and activates storage only after an atomic audit succeeds.

API: `project_progress_migrate(password)`; `project_progress_staff_get(job, page=0, focus='', touch=true)`; `project_progress_client_get(job, client, page=0, focus='', support=null, touch=true)`; `project_progress_save(job, client, request_id, expected, fields)`. Saves return existing/new project ID, final event ID and replay status. Native storage remains inaccessible through HTTP until the subsequent route/form integration. Native synthetic evidence must cover real PDO transactions, current grants, cross-client reads, concurrent writers/retries and revocation while waiting, audit rollback, exact legacy adoption, history/request/current-row corruption, preparation refusal and bounded pagination.
