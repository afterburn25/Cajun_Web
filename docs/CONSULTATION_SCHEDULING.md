## Intended workflow

One studio consultation calendar, with owner-configured IANA timezone, one availability window per selected weekday, slot length, buffer and minimum notice. Scheduling starts disabled with no offered hours; no business availability is invented. Owners explicitly enable it after setup. A bounded 30-day window limits public work. Reuse canonical weekly rules and UTC half-open intervals; show explicit zone/offset in public slot labels and saved staff records. Daylight-saving gaps are omitted and repeated local times use the documented first occurrence.

The existing consultation request page stays available when scheduling is disabled/unprepared, retaining date/time preferences and the truthful statement that no slot is reserved. When enabled, visitors choose an offered slot and their display timezone. Existing contact validation, consent, CSRF, honeypot, form timing, rate limits and one-use request identities stay in force. Saving a request and its structured appointment is atomic. A requested slot blocks a competing request, but remains pending staff confirmation. Public success states that the request was saved and is not confirmed; no meeting link, calendar-provider connection or delivered confirmation is invented.

Staff with current website permission use the existing inquiry to explicitly adopt a legacy consultation request into a chosen available slot, confirm a pending future request, decline/cancel it or reschedule an active future appointment. Existing lead text and inquiry sales status remain separate. Rescheduling returns to requested and requires fresh confirmation. Confirmation rechecks current consent, availability/conflicts, exact revision and current staff password. The page clearly distinguishes an internal scheduling decision from contacting the prospect. This increment sends no confirmation/cancellation mail and offers no public cancellation token; prospects contact the studio and authorized staff record the change.

## Persistence and authorization

Add InnoDB configuration, appointment and retained revision tables under existing database modules. Appointment lead identity is unique and foreign-key linked to the existing inquiry; explicit permanent inquiry deletion removes dependent personal appointment content. No legacy free-text parsing or automatic adoption. Owner setup validates columns, indexes and foreign keys, refuses unknown populated tables, is idempotent and records strict audit/readiness after DDL. Fresh installation prepares empty disabled scheduling.

Every conflict-changing write locks the same database configuration row before reading active appointments and writing. Public requests, staff adoption/rescheduling/transitions, configuration changes and inquiry deletion must use a consistent order. Staff mutations also take the existing staff mutex and recheck current authenticated permissions/session/support boundaries. Current state, monotonically increasing revision, immutable snapshot and strict audit commit together; stale forms retain their submitted revision. Do not trust a slot offered by an earlier GET. Strict audit failure rolls back intake and scheduling changes. File recovery preserves database history.

Configuration changes preserve existing appointments; reject changes that create conflicting future appointments under a new buffer. Confirmation and rescheduling revalidate current availability, duration and conflicts. Minimum notice applies to new requests and rescheduling, not confirmation of an already held future slot; if hours/duration have changed, staff must choose a currently available slot before confirming. Terminal states never reopen. History and private contact data are current-authorized and paginated; anonymous availability contains only offered slot times.
