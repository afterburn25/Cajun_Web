# Importing 20i hosting drafts

This increment adds an owner-only **Import hosting products** panel to the service catalog. It uses named hosting types already present in the latest saved 20i hosting inventory. It creates local hosting drafts; it does not import the complete 20i product catalog, provider prices, available stock, billing periods, images or order capabilities.

1. Enable the service catalog and 20i inventory, save the General API key, and explicitly refresh hosting inventory.
2. In the catalog, enable imports after confirming a current backup and your owner password.
3. Choose a named type, unique local SKU and local service period. Confirm creation with your current owner password.
4. Review and edit the draft's price, description and service terms, then upload your own JPG, PNG or WebP image. Images may be replaced or detached. They are accessible through their existing media URL even while the product is a draft; do not upload private customer records.

Imported products must remain in the hosting family and draft or retired state. Existing hosting publication, quoting and checkout restrictions remain enforced server-side, including a forged family change. Unrelated catalog products retain their existing save and publication behavior. Repeated imports preserve the original product, wording, prices and image. An import made with earlier credentials is clearly labelled and cannot be silently reused after connection details change. A credential fingerprint fences the context; it does not establish a provider account identity.

## Source and authority

The documented `GET /package` fields `typeRef` and `packageTypeName` are the only imported provider product facts. See the [official package listing example](https://docs.20i.com/api/retrieve-packages-api) and [retained owner requirements](TWENTYI_REQUIREMENTS_EVIDENCE.md). A successfully parsed saved response is not proof of account-wide catalog coverage. Missing names are skipped; conflicting names for the same type refuse the preview.

The latest intent must have a complete result with no skipped packages, the current profile revision and credentials. No older successful result is silently substituted. Current owner authorization, support exclusion and selected preview identity are rechecked under the staff mutex and transaction before creation. Provenance retains the profile, revision, saved observation, type, original name and installation-bound credential fingerprint; it never exports the provider key. Ordinary provenance hashes, row counts and matching audit records detect inconsistent retained history; they are not a claim of cryptographic tamper-proof history.

Only a new additive import table and explicit preparation markers are created. Missing established history refuses re-creation. Unprepared reads do not prepare storage. Existing catalog validation, revisions and audit writes are shared through an internal writer requiring the owning mutex and transaction. Public catalog fields and invoice snapshot/quote functions are unchanged.

## Images and housekeeping

Images use the existing genuine multipart upload, size/type/pixel validation and server re-encoding. No remote URL fetch or invented image endpoint is added. A failed import-image transaction removes only the new file allocated by that request; old files and the old image reference are retained. Detaching an image does not delete its file immediately.

Cleanup takes the same staff mutex as preparation/import/image replacement, then rechecks current `staff.manage`, validates the complete import store and reads media before deleting anything. Thus cleanup either finishes before a new import/image attachment or observes that attachment after acquiring the mutex; it cannot reuse a pre-lock false readiness result. This serialization is source-reviewed; the current native fixture separately tests duplicate import contention, not a timed cleanup race. Existing project, marketing, filename and symlink safeguards remain.
